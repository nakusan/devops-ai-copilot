扩展性不能靠「把 Compose 里的 replica 改成 3」。这个工程里，**有的层加副本立刻有效，有的层加了会静默出错，有的层加了也解决不了你刚碰到的 429**。下面按这个仓库的真实耦合来评。

---

## 先定性：现在哪些已经是无状态的

对话真相源在 PostgreSQL，配额和限流在 Redis，文件在 MinIO，重活在 Kafka。这四样是按可水平扩展来设计的，而且代码大体守住了：

- 每个聊天是一次长 `POST` + SSE，**不是**先建连再往别的请求推事件。所以 **control-plane 多副本之间不需要会话粘滞**——下一句可以落到另一台 Java，history 从 PG 再读。
- LangGraph 无 checkpointer，状态全在这一次 `ainvoke` 的内存里，Python HTTP 进程本身也无会话粘滞需求。
- Worker 已经和 HTTP 拆开，注释里写了「可单独扩缩容」——方向对。

所以「单节点」主要是 **部署形态是单副本**，不是「架构只能单机」。生产要做的是：把已经无状态的服务扩出去，把还绑在进程内存里的点改掉，再给中间件做高可用。

## 真正绑死扩展的点（加副本会坏）

**1. 取消注册表是进程内字典**

```10:25:ai-plane/app/graph/streaming/cancel_registry.py
class CancelRegistry:
    def __init__(self) -> None:
        self._events: dict[str, asyncio.Event] = {}
    def cancel(self, session_id: str) -> bool:
        ev = self._events.get(session_id)
```

Java 断 SSE 时另打一枪 `POST /internal/v1/chat/cancel`。今天 `AI_PLANE_BASE_URL` 指向唯一实例，能打中。前面挂负载均衡后，**流在 Pod A，cancel 打到 Pod B，B 上没有这个 Event，取消静默失败，继续烧 token**。

这是扩 ai-plane 的第一块绊脚石。生产要改成 Redis Pub/Sub（或 Redis key + 本进程订阅）：cancel 广播，持有该 stream 的那台自己 set Event。按 `sessionId` 还不够，同一会话并发两路时会互相覆盖，应用 **请求级 id / traceId**。

**2. Kafka 默认 1 分区，Worker 加副本等于空转**

Consumer 用了 group（`ai-plane-ingest-v1`），这是对的。但 Compose 里 Kafka 是单 broker，topic 多半是自动创建的 **1 分区**。同 group 里多出来的 Worker 会一直 idle。生产必须显式建 topic，例如 knowledge/analysis 各 12–24 分区，副本因子 3。Worker 数 ≤ 分区数。

消息 key 已经是 `documentId` / `jobId`，同一文档有序，这点可以保留。

**3. 连接池按单进程写死**

Java Hikari `maximum-pool-size: 10`，Python pgvector `asyncpg` `max_size=4`。3 个 Java × 10 = 30 条连到 PG，再加上检索只读池。现在库是单机 Postgres，连接先被打满，QPS 还没上去。扩应用副本前必须先定 PG `max_connections`、把只读查询打到 **只读副本**（你们已经有 `copilot_ro`，这条路是铺好的）。

**4. 上传走 Java 本地 multipart（知识库 20MB / 分析 100MB）**

文件进 JVM 再转 MinIO。多副本能分流，但每个 Pod 的内存、超时、磁盘仍被大文件绑住。生产主流是 **Presigned PUT 直传 MinIO**，Java 只收 confirm 再发 Kafka。设计文档写过，代码没做。不改这个，分析上传会先把 control-plane 拖死，而不是先把 Worker 拖死。

**5. MCP stdio 每调一次起一个子进程**

ai-plane 一扩，每个副本乘以并发 tool call，FD 和 fork 会先爆。生产要长连接（Streamable HTTP MCP）或边车，不能跟副本数线性 fork。

## 按负载类型分别扩（生产不该「整栈一起乘 3」）

这个系统其实是 **四条不同的伸缩曲线**，混在一起扩会浪费钱、也扩不对瓶颈。

### A. 在线对话（SSE + LLM）—— 真正的瓶颈几乎不在你们的代码

一条对话 ≈ 1 个 Tomcat 异步请求 + 1 条 Java→Python 长连接 + 1 次智谱流式调用，持续数秒到几分钟。

| 层 | 怎么扩 | 上限在哪 |
|----|--------|----------|
| control-plane | Deployment 多副本，HPA 看 **活跃 SSE 数 / JVM 堆**，不是 QPS | 每条 SSE 占一个异步槽；5 分钟超时意味着峰值连接数 ≈ 5min 内发起的对话数 |
| ai-plane HTTP | 同样 HPA；uvicorn workers 要算清楚（每个 worker 一个事件循环） | **Cancel 不改就不要扩到 >1** |
| LLM | 这才是天花板 | 供应商 RPM/TPM。副本从 1 变 10，429 会多 10 倍 |

生产对话扩容的正确顺序是：

1. **全局并发闸门**（Redis 信号量或队列）：全集群同时只有 N 路在打智谱，超出的排队或快速失败。  
2. 多模型 / 多 Key 池，熔断。  
3. 再扩 Java/Python 副本去扛 SSE 连接。

只扩 Pod、不闸 LLM，就是把单机 429 变成集群 429。

可选的进一步拆法（中大团队才值得）：把「编排+检索」和「纯 LLM 代理」分开。现在 `ainvoke` 和 `stream_chat` 在同一进程，embedding 检索会和 token 流抢循环。你们已经把 Worker 拆走了，下一步才是把 LLM 网关独立（或用 Envoy 外挂）。多数公司做到闸门 + 多副本就够。

### B. 知识入库 / 分析（Kafka Worker）—— 这是最该先水平扩的

这条链路 **天生可扩**，也是架构里最接近生产的部分。

生产形态：

- knowledge Worker、analysis Worker **分开 Deployment**（已有 `WORKER_ROLES`，直接能拆）。  
- knowledge 吃 CPU+embedding API；analysis 吃 IO+临时盘。伸缩比不同，不该共一个 HPA。  
- 分区数按目标吞吐估：embedding 批量 32、单文档数秒到几十秒。若要「同时消化 20 份文档」，至少 20 分区、20 个 knowledge 副本（再乘 embedding 限流）。  
- **消费并行度不要靠把 `max_records` 调很大**：现在单进程顺序处理 batch，加大 batch 只延长 commit 间隔，失败重试成本更高。要吞吐就加分区 + 加进程。  
- 大文档 chunks 一次 HTTP 回 Java：扩 Worker 后会把 control-plane 和 PG 写打满。生产应分批 `COPY` 或给 Python 独立写入角色。

### C. RAG 检索 —— 扩应用容易，扩向量库难

检索是 Python 只读 PG。ai-plane 多副本 = 多条读连接，**读副本**才能跟。

pgvector HNSW 在单主上百万向量通常还能打，再往上行业会迁 **专用向量库**（Milvus / Qdrant / OpenSearch kNN），或 PG 分区 + 只读副本。现在 `team_id` 过滤是查询里的硬条件，索引要按 `(team_id)` 或 partial index 规划，否则一扩 QPS，全表向量扫会先把主库 IO 打满。

### D. 中间件 —— 应用副本的前提，不是应用扩完再补

Compose 里每样都是单节点：Kafka `replication.factor=1`、单 Postgres、单 Redis、单 MinIO、单 Tempo。生产最低配：

| 组件 | 生产基线 | 不配的后果 |
|------|----------|------------|
| Postgres | 主 + 同步/异步只读；连接池中间件（PgBouncer） | 应用一扩就耗尽连接 |
| Redis | 哨兵或集群；配额 key 的 TTL 你们已有 | 挂了限流/配额失效或聊天拒绝 |
| Kafka | 3 broker，RF=3，min.insync=2 | 单盘坏了入库全停 |
| MinIO | 分布式 4 节点起 | 对象丢了知识源文件没了 |
| 追踪 | Collector + 尾采样，采样率 <1 | 全采样在对话流下会比业务还重 |

这些没有弹性，前面谈 HPA 没有意义。

## 一张生产拓扑（按这个仓库演进，而不是推倒重来）

```
                    ┌─ Ingress / API Gateway ─┐
                    │  超时预算、全局限流      │
                    └──────────┬──────────────┘
           ┌───────────────────┼───────────────────┐
           ▼                   ▼                   ▼
    control-plane ×N      （静态 web）         不暴露 ai-plane
    (SSE 终点, JWT)              │
           │  NDJSON            │
           ▼                    │
     ai-plane HTTP ×M  ←── Redis cancel bus
     (检索 + 编排 + LLM 闸门)
           │
           ├─ 只读 PG（pgvector 副本）
           └─ LLM 供应商 /  embedding
           
    control-plane ──Kafka──► worker-knowledge ×P
                           ► worker-analysis ×Q
                              │
                              └─ 写：仍经 Java Internal 或独立写账号
```

Ingress 只对 Java；Python 保持 ClusterIP。这和现在「客户端只调 Java」一致，扩容时不要把 ai-plane 暴露出去图省事。

## 建议的落地顺序（避免一上来上 K8s 全集群）

**阶段 0 — 现在就能做、不扩副本也有用**  
LLM 全局并发限制、429 熔断、cancel 改 Redis、Kafka 显式分区。这四件决定「能不能扩」。

**阶段 1 — 只扩 Worker**  
入库慢、聊天还行时，只加 knowledge Worker + 加分区。收益最大、风险最小。

**阶段 2 — 扩 control-plane + ai-plane HTTP**  
前提：cancel 已跨进程、连接池和 PG 只读副本就绪、LLM 有闸门。HPA 指标用 **活跃流数 / 排队延迟**，不要用 CPU（SSE 连接 CPU 很低，会扩不起来或乱扩）。

**阶段 3 — 中间件 HA + 对象直传**  
Kafka/PG/Redis/MinIO 多节点；上传改 presigned。到这一步才像生产。

**阶段 4 — 检索与模型层**  
向量库分离或 PG 读扩展；embedding/LLM 独立网关。这是量到「每秒几十次问答、知识库 GB 级」才需要的。

---

## 容量直觉（避免空谈「能扛多少」）

以智谱免费/低档为例，RPM 往往几十到一两百。假设 60 RPM、平均一轮 4s 流式：

- 全集群同时在飞的对话 ≈ `60 * 4 / 60 = 4` 路  
- **4 路对话，1 个 Java + 1 个 Python 都嫌多**，扩副本零收益  

若换成企业合同档 600 RPM、平均 8s：

- 同时在飞 ≈ 80 路 SSE  
- Java 2–3 副本、Python 2–3 副本开始有意义  
- Worker 仍按「每天入库文档数 / 单文档耗时」单独算，和聊天副本无关  

所以生产扩展性首先是 **把聊天并发和入库吞吐当成两个产品指标**，不要用「用户数」一个数字去乘所有 Deployment。

## 总评

扩展性设计 **骨架是对的**（无状态 API、Kafka 卸货、Redis 做共享计数、读写账号分离），**运行时按单进程假设写死了几处**（CancelRegistry、1 分区、小连接池、multipart 进 JVM、stdio MCP、无 LLM 闸门）。

和业界生产 AI 网关（OpenAI 兼容代理 + 队列、KServe/vLLM 扩推理、Celery/Kafka worker 扩 ingest）比：你们缺的不是 Kubernetes YAML，而是 **跨实例的取消与限流**。那两块不改，副本数只是把单机缺陷复制 N 份。

若只选一件为扩容做准备：把 `CancelRegistry` 换成 Redis 广播，同时给 LLM 加集群级信号量。没有这两样，不要把 ai-plane 扩到 1 以上。
