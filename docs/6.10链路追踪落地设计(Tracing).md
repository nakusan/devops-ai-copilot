## 1. 决策记录（ADR 摘要）

以下 6 项已确认，本文全部按此展开。

| # | 决策点 | 选定方案 | 理由 | 被否方案与原因 |
|---|--------|----------|------|----------------|
| D1 | Java 接入 OTel 方式 | **micrometer-tracing-bridge-otel 代码级接入** | Spring Boot 3.3 官方路线；改动可控可审计；`AiPlaneClientConfig.java:21` 已用注入的 `WebClient.Builder`，traceparent 自动注入天然可用 | OTel Java Agent：零代码但镜像变大、启动变慢，且会与现有 `TraceIdFilter` 争夺 traceId 主导权，产生「两套 traceId」 |
| D2 | 观测后端范围 | **只加 Tempo，应用直连 OTLP** | 组件最少、Traces 立刻可用；Grafana 已在位可复用 UI 与 datasource 体系 | Loki/Alloy 与 OTel Collector 均延后：Collector 的价值（尾采样、多后端、脱敏）当前一个都用不上，早加只是多一跳故障点 |
| D3 | 前端是否纳入链路 | **不纳入，链路从 Java 网关起** | `web/` 是原生 JS + Vite，无构建期框架，接 OTel Web SDK 收益低于成本 | 前端 RUM 列入 V2（§12） |
| D4 | Kafka 异步链路建模 | **parent-child** | 上传→入库在 UI 上呈现为一棵树，排障最直观 | span link 语义更严谨，但需在两条 trace 间跳转，MVP 阶段增加认知负担；取舍已知（§9 R4） |
| D5 | 实施节奏 | **分 4 阶段，每阶段独立验收** | P1 半小时见效，可先拿到收益再推进 Java 改造 | 一次性全量落地风险集中，Java 侧 Filter 顺序问题会阻塞整体验收 |
| D6 | Trace 后端选型 | **Grafana Tempo** | 复用现有 Grafana；支持 TraceQL 与 trace→metrics 跳转 | Jaeger 需额外维护独立 UI |

### 5.2 `otel.py` 规格

保持现有 `setup_otel(service_name, otlp_endpoint)` 签名不变，增加三处：

1. **Resource 补充环境与版本**，便于 Grafana 按环境筛选：

```python
resource = Resource.create({
    "service.name": service_name,
    "service.version": settings.service_version,      # 新增配置项，默认 "0.1.0"
    "deployment.environment": settings.deploy_env,    # 新增配置项，默认 "dev"
})
```

2. **显式声明 sampler**，避免依赖隐式默认值：

```python
from opentelemetry.sdk.trace.sampling import ALWAYS_ON, ParentBased, TraceIdRatioBased

# 低流量全采样；Java 侧采样决策通过 ParentBased 被尊重（见 §9 R6）
sampler = ParentBased(root=ALWAYS_ON if settings.otel_sample_rate >= 1.0
                      else TraceIdRatioBased(settings.otel_sample_rate))
provider = TracerProvider(resource=resource, sampler=sampler)
```

3. **新增 `shutdown_otel()`**，内部调 `provider.shutdown()`（会触发 BatchSpanProcessor 的最终 flush）。模块级保存 provider 引用。

4. **流式噪音抑制（P1 补丁 / F4）**：`instrument_fastapi` 调用时传入
   `exclude_spans=["send", "receive"]`，去掉 ASGI 每次写出/读入的子 span，
   保留 server span + 业务手工 span（`internal.chat` / `rag.retrieve` / `llm.completion`）。

### 5.3 `worker.py` 规格（修 F3）

`_run()` 的收尾处（`logger.info("worker stopped cleanly")` 之前）调用 `shutdown_otel()`。

**为什么必须做**：BatchSpanProcessor 默认 5 秒调度一次，worker 收到 SIGTERM 后如果直接退出，最后一批 `ingest.process` span 会连同缓冲区一起丢失——而入库失败恰恰是最需要看 trace 的场景。FastAPI 进程可依赖 lifespan，但 worker 是裸 `asyncio.run`，必须显式处理。

### 5.4 `logging.py` 规格（修 B5）

`_resolve_trace()`（当前 `logging.py:38-46`）的优先级必须翻转：

```python
def _resolve_trace(record):
    trace_id, span_id = _current_trace_context()   # OTel 当前 span 优先
    if not trace_id:                                # 仅在无活跃 span 时兜底
        trace_id = str(record.__dict__.get("trace_id") or "")
    if not span_id:
        span_id = str(record.__dict__.get("span_id") or "")
    return trace_id, span_id
```

**为什么**：`extra["trace_id"]` 装的是 Java 业务字段（`InternalChatRequest.trace_id`），P2 完成前它与 OTel 的 trace_id 是两个体系。如果日志显示业务 traceId 而 Tempo 里存的是 OTel traceId，「复制日志里的 id 去 Tempo 搜」这个最核心的排障动作会失效。

业务 traceId 不丢弃——它作为 span 属性 `copilot.trace_id` 保留（`orchestrator.py:33` 已经这么做了），在 Tempo 里可用 `{ span.copilot.trace_id = "..." }` 反查。

## 6. P2 — 把 Java 接进同一棵树

**预计工作量**：1 天（含测试调整）。
**风险等级**：中——涉及 Filter 顺序调整，见 §9 R2。

### 6.4 `TraceIdFilter` 重构规格（**本阶段最容易踩坑处**）

改造后职责收敛为一件事：**把当前 span 的 traceId 写进响应头，维持 `X-Trace-Id` 业务契约**。traceId 的生成、传播、MDC 注入全部交给 micrometer-tracing。

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 2)   // ← 关键：必须晚于 ServerHttpObservationFilter
public class TraceIdFilter extends OncePerRequestFilter {

    private final Tracer tracer;   // io.micrometer.tracing.Tracer

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        Span current = tracer.currentSpan();
        String traceId = current != null ? current.context().traceId() : fallbackTraceId();
        // micrometer 已把 traceId/spanId 写进 MDC；此处仅兜底，保证 tracing 关闭时日志与响应头仍有值
        TraceIds.set(traceId);
        response.setHeader(TraceIds.HEADER_X_TRACE_ID, traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            TraceIds.clear();
        }
    }
}
```

**Order / 实际挂载说明**：设计书要求 `@Order(HIGHEST_PRECEDENCE + 2)` 晚于 `ServerHttpObservationFilter`（`+1`）。本项目通过 `FilterRegistrationConfig` **禁用了** TraceIdFilter 的 Servlet 自动注册，仅在 `SecurityConfig` 的 Security 链中 `addFilterBefore(..., UsernamePasswordAuthenticationFilter)`，而 Security `FilterChainProxy` 默认 order 约为 `-100`，**天然晚于** ObservationFilter。因此 `tracer.currentSpan()` 在 Filter 内通常可用；`@Order(+2)` 与设计书保持一致，作文档与潜在重新注册时的保险。

`fallbackTraceId()` 保留一个 `UUID.randomUUID().toString().replace("-", "")` 的降级路径，用于 `management.tracing.enabled=false` 的回滚场景（§11）。

> 补充说明：网上常见「`@Order` 对 Filter 无效」的说法，指的是**在返回 `FilterRegistrationBean` 的 `@Bean` 方法上**加注解的情形。本项目的 `TraceIdFilter` 是 `@Component` 组件扫描出来的 `Filter` Bean，Spring Boot 通过 `AnnotationAwareOrderComparator` 读取类上的 `@Order`，改数值即可生效，不需要改造成 `FilterRegistrationBean`。

from opentelemetry.trace import SpanKind

def _carrier(msg) -> dict[str, str]:
    # aiokafka headers 是 tuple[(str, bytes), ...]
    return {
        k: (v.decode("utf-8") if isinstance(v, bytes | bytearray) else str(v))
        for k, v in (msg.headers or ())

async def _process_one(msg, producer) -> None:
    ctx = extract(_carrier(msg))

        f"{msg.topic} receive", context=ctx, kind=SpanKind.CONSUMER

        span.set_attribute("messaging.system", "kafka")
        span.set_attribute("messaging.destination.name", msg.topic)
        span.set_attribute("messaging.kafka.partition", msg.partition)
        span.set_attribute("messaging.kafka.offset", msg.offset)
        ...  # 原有解析与重试逻辑不变

## 9. 风险与陷阱清单（实施前必读）

### R1 — 异步生成器跨 `yield` 持有 span（**P1 已实测**）

`run_diagnosis_stream`（`orchestrator.py:22-138`）是 **async generator**，而 `with _tracer.start_as_current_span("internal.chat")`（`:30`）包裹了整个函数体，中间有多次 `yield`。`stream_chat` / `_openai_stream`（`llm_client.py:108-178`）是同样的结构。

问题在于：Python 的异步生成器**不拥有独立的 contextvars 上下文**，它借用恢复它的那个任务的上下文。OTel 的 `start_as_current_span` 靠 `attach()` / `detach()` 一对 token 维护当前 span，当生成器在 A 任务被创建、在 B 任务被恢复和关闭时，`detach()` 可能在与 `attach()` 不同的上下文里执行。典型症状：

- 日志里出现 `Failed to detach context` 警告
- span 的 parent 挂错，或 `internal.chat` 永不结束（trace 一直显示进行中）
- 后续无关请求的 span 被错误地挂到上一条 trace 下

**P1 实测结论（2026-08-12，`tests/observability/test_logging_trace.py::test_r1_async_generator_span_parent_child`）**：

在**同一 asyncio 任务内**用 `async for` 消费生成器时：

- `llm.completion` 正确挂在 `internal.chat` 下（`child.parent.span_id == parent.context.span_id`）
- 两个 span 均正常 `end`（非永不结束）
- yield 之后回到 parent 上下文仍正确

因此 **P1 不预先按方案 B 重构**。生产联调时若出现 `Failed to detach context` 或 Tempo 中 span 悬挂，再改方案 B：

```python
# 方案 B：不跨 yield 持有 "current span"，改为显式传递 context
span = _tracer.start_span("internal.chat")
ctx = trace.set_span_in_context(span)
try:
    # 需要成为子 span 的地方显式传 context=ctx，而不是依赖隐式 current
    ...
finally:
    span.end()
```

代价是子 span 需要显式接收 `context` 参数（`graph.ainvoke` 内部的节点要通过 state 或 contextvar 传递），改动面比方案 A 大。

### R2 — Java Filter 顺序（P2 已澄清）

见 §6.4。本项目 `TraceIdFilter` **仅挂在 Security 链**（Servlet 自动注册已禁用），天然晚于 `ServerHttpObservationFilter`，`tracer.currentSpan()` 可用。若将来重新启用 Servlet `FilterRegistrationBean`，必须保持 order ≥ `HIGHEST_PRECEDENCE + 2`，否则响应头会落到 fallback 随机 id，与 Tempo 对不上（P2-2 联调项）。

### R3 — SSE 场景下 server span 的生命周期

Java 的 `ServerHttpObservationFilter` 在异步分发（SSE）下，span 的结束时机取决于容器的 async 完成回调。若发现 Java span 的 duration 远小于实际 SSE 持续时间，不要试图强行拉长——端到端耗时以 `chat_stream_duration_seconds` 指标为准，trace 用于看**分段**耗时。这是已知的取舍，写进排障手册即可。

### R4 — parent-child 建模导致 trace 时间跨度很长（D4 的已知代价）

文档上传后若 Kafka 消费延迟或重试，`ingest.process` 可能在几分钟后才产生 span，挂在早已结束的上传请求 trace 下。Tempo 按 traceId 组装，晚到的 span 不会丢，但 UI 上这条 trace 的总时长会显示成「几分钟」，看起来像慢请求。

**缓解**：在 Dashboard 的慢请求面板里用 `{ resource.service.name = "control-plane" && name =~ "POST /api/v1/sessions.*" && duration > 5s }` 限定到聊天链路，不要用全局 duration 过滤。

### R5 — Tempo 卷权限与磁盘

`grafana/tempo` 镜像默认非 root 运行，挂载本地卷时可能因权限写不进去（表现为容器反复重启、日志报 `permission denied`）。§4.3 已用 `user: "0"` 规避，生产环境应改为预先 chown。`block_retention: 48h` 已设，避免本地磁盘无限增长。

### R6 — 采样率的跨语言联动

Python 的 sampler 是 `ParentBased`，**会尊重上游传来的采样标志**。这意味着：Java 采样率设为 0.1 后，Python 也只会有 10% 的 trace，不是 Python 配置错了。调采样率只需动入口侧（Java）。反过来，worker 消费 Kafka 时的父上下文来自 Java 生产侧，同理。

### R7 — 性能开销

100% 采样 + BatchSpanProcessor 在当前流量下开销可忽略（每请求约 10 个 span，序列化成本远小于一次 LLM 调用）。真正的风险是**埋点粒度失控**——§7.5 已明确禁止对 SSE 每个 token 建 span。新增埋点时的判据：**这个 span 会不会在单条 trace 里出现超过 50 次？** 会就改用 span event 或指标。

### R8 — 密钥与隐私

span 属性遵守 §3.3 红线。特别注意 httpx 自动埋点默认不记录请求体（安全），但**不要**开启 `OTEL_PYTHON_LOG_CORRELATION` 之外的 body 捕获选项。Tempo 未加认证，仅监听 Compose 内网与本机端口，不得暴露到公网。

## 11. 回滚与开关矩阵

每个阶段都可独立回滚，且**回滚不需要改代码**。

| 阶段 | 关闭方式 | 关闭后的状态 |
|------|----------|--------------|
| P1 | 移除 `ai-plane` / `ai-plane-worker` 的 `OTEL_EXPORTER_OTLP_ENDPOINT` | 回到 B1 状态：span 仍创建但不导出，业务零影响（`otel.py:44-46` 的降级分支） |
| P2 | `management.tracing.enabled=false`（或 `TRACING_SAMPLE_RATE=0`） | Java 不再产生 span，`TraceIdFilter` 走 `fallbackTraceId()`，`X-Trace-Id` 契约不破 |
| P3 | `spring.kafka.template.observation-enabled=false`；Python 侧 `extract` 拿不到 header 时自动降级为新建根 span | Kafka 链路回到断开状态，消费逻辑不受影响 |
| P4 | 移除 Prometheus 的 `--enable-feature=exemplar-storage` | 指标正常，仅失去跳转能力 |
| 全量 | `docker compose stop tempo` | 应用侧 OTLP 导出失败会被 exporter 内部吞掉并重试，**不影响业务请求**（已验证 exporter 异常不外抛） |

**兜底原则**：可观测性组件的任何故障都不得影响业务链路。P1 的 `otel.py:41-43` 已有 exporter 初始化失败降级到 Console 的处理，实施时保持该行为。
