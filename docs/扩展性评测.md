## 总体判断

这是一份**完成度很高的企业训练型 MVP**，不是半成品脚手架，也还不是能扛生产流量的 AI 平台。

架构选择（Java 控制面 + Python 智能面、SSE 对外、Kafka 做重活、PG 当对话真相源、OTel 贯通）在**国内企业内源/中后台**里是主流写法，和阿里、银行、运营商那套「网关不进 Python」一致。和 **Dify / FastGPT / LangGraph Cloud** 这类 AI 原生产品比，它更像「把 AI 嵌进已有 Java 业务系统」，而不是「以 Agent 为中心的应用」。

文档写得很清楚：目标是练事件驱动、流式、跨语言协同，不是一次做成 Dify。按这个目标，骨架是对的。真正的问题是：**协议和组件的名字已经是 2025 主流，运行时行为仍停在 2023 规则引擎。** MCP、LangGraph、RAG 都有这个落差。

---

## 做得对的地方（先说，避免评测只剩挑刺）

1. **边界清晰且代码守住了。** 客户端只打 Java；Python 无 PG 写权限；对话 history 每轮由 Java 传入，不在 Python 里另存一份记忆。这比很多「两边各写一套 session」的双栈项目干净。
2. **同步和异步拆开了。** 聊天走 HTTP 流，入库/分析走 Kafka + 独立 Worker，避免 embedding 把 SSE 事件循环堵住。这是正确的。
3. **流式协议选择合理。** 对内 NDJSON、对外 SSE、Java 做终点：便于鉴权、落库、取消、审计。OpenAI 自己的 ChatGPT 也是网关持有用户连接。
4. **聊天幂等有设计。** `clientMessageId` + 已有 assistant 直接回放，流式请求故意不重试。这是懂流式坑的人写的。
5. **可观测性在 MVP 里算超配。** Trace 能从 Java HTTP 跟到智谱 429，这已经比不少「生产系统」强。

这些是工程基本功，后面的缺陷是在这个基础上的能力缺口，不是架构选错了。

## 一、服务间消息与协调

### 现状：三条总线，职责清楚

| 通道 | 用途 | 评价 |
|------|------|------|
| Java → Python NDJSON | 聊天主路径 | 合适 |
| Java → Python HTTP cancel | 客户端断开 | 协议有，传播不完整 |
| Python → Java Internal HTTP | 写 chunks / 改 job 状态 | 符合「Python 不写库」，但多一跳 |
| Kafka knowledge/analysis | 重活解耦 | 合适，运维面没做完 |

Kafka 生产端 `acks=all` + 幂等，消费端手动 commit + 进程内重试 3 次再进 DLQ，这套是教科书 MVP。

### 缺陷（按严重程度）

**1. 取消只覆盖 LLM 流，图执行不可中断（协调层最大的洞）**

`graph.ainvoke()` 跑完才看 `cancel_event`。用户关掉页面时，RAG embedding、MCP stdio、分析查询仍会跑完。行业做法是：图节点轮询 cancel / 用 `asyncio.Task.cancel()`，或 LangGraph 的 interrupt。现在 cancel 接口存在，语义是「尽量取消生成」，实际是「生成开始前取消无效」。

**2. 没有统一超时预算**

WebClient 读 120s、LLM 60s、MCP 5s、Java 回调 30–120s，各算各的。一次聊天没有「还剩多少毫秒必须结束」。上游 429 重试 1 秒再打，会把整段 SSE 拖到数秒（你 Tempo 里 5s 那次就是）。主流网关（Envoy / Spring Cloud Gateway）会把 deadline 往下传；这里没有。

**3. LLM 429 几乎没被当成一等故障**

只 catch `RateLimitError`、sleep 1s、最多 2 次。没有熔断、没有按模型的令牌桶、没有降级到 mock/备用供应商。智谱免费档被打满是必然事件，不是偶发。行业现在至少会：指数退避 + `Retry-After` + 熔断 + 多模型 fallback。

**4. Kafka 无效消息被 commit 掉**

JSON 解析失败：打日志然后 `return`，外层照样 `commit()`。坏消息从队列消失，DB 里 job 可能永远 `PENDING`。正确做法是进 DLQ 或至少 PATCH `FAILED`。这是会丢数据的。

**5. DLQ 是「话题」不是「能力」**

有 `*.dlq.v1`，没有消费、没有重放、没有和 job 状态打通。失败三次后 Java 侧可能已经是 `FAILED`（handler 里会 PATCH），也可能卡在 `PROCESSING`，运维只能翻 Kafka。Outbox 也没做：Java 是同步 `future.get(10s)`，Kafka 短暂不可用会让上传 API 直接 500。本地测试能接受，一上共享 Kafka 就会痛。

**6. 入库写路径绕一圈**

Worker 已经连着只读 PG，写 chunks 却要 HTTP POST 回 Java 再 INSERT。架构原则（P2）是对的，代价是：大文档一次 POST 全量、超时 120s、Java 成了向量写入瓶颈。行业常见折中：Python 用独立写入账号（仍不是业务账号），或 Java 提供 `COPY`/分批。现在「先删后插」整批替换，并发重入会互相踩。

**7. 跨服务没有背压**

SSE 依赖 TCP 自然减速。前端慢、Java 缓冲、Python 继续向智谱要 token——中间没有高水位。NDJSON 还要求上游每行 flush，协议注释里自己也写了「不换行就会卡住」。这是已知的脆弱点。

**8. 会话级 cancel 注册会互相覆盖**

`CancelRegistry` 按 `sessionId` 存一个 Event。同一会话连发两条（或重连）会覆盖旧 Event，旧流可能取消不掉。应按 `traceId` / 请求 id 登记。

## 二、程序编排：看起来像 Agent，跑起来像流水线

LangGraph 在这里是 **硬编码 DAG**：router → (retrieve | tool | fan_out | analysis) → synthesize → END。没有循环、没有 checkpoint、没有 interrupt、没有 ReAct。

这在 2024 年初还能叫 Agent。2025 年业界主流已经是：

- **LLM 决定下一步**（tool calling / function calling）
- **多轮工具循环**直到模型说 stop
- **checkpoint** 支持断点续跑、人机确认
- 复杂的才上图；简单 RAG 用一条链就够

你们的图其实做了三件事：规则分类 → 拉上下文 → 拼 prompt。`synthesize` 节点甚至不调 LLM，真正的生成在图外（模式 A）。这是为了 SSE 好推 token，工程上说得通，但意味着 **LangGraph 没有发挥状态机价值**，换成几个 `async def` + `asyncio.gather` 行为几乎一样。

规则路由的具体问题：

- 默认偏 RAG（没匹配上也走检索），所以「你好」也会 embed + 查库。
- 工具路径是关键词（CPU、QPS、连接数）；没命中还 **默认打一条 `db_connections`**。用户问「用 MCP 查一下」可能拿到毫不相干的连接数。
- 没有 `rag_then_tool`（先检索再决定调不调工具），而运维场景恰恰需要「先看手册再查监控」。
- 分析路径只取「该用户最近一次 COMPLETED」，用户说「分析刚才那个 heap」时，指错任务的概率不低。

并行 `fan_out` 是加分项，方向对。缺的是 **工具结果回灌后再检索/再思考**，现在是单次射击。

## 三、MCP：协议选对了，用法还没到「MCP」

MCP（Model Context Protocol）的业界用法是：

1. 模型看到工具 JSON Schema
2. 模型输出 `tool_call`
3. 运行时按 schema 调 MCP server（stdio / Streamable HTTP）
4. 结果回给模型，可能再调

你们现在是：

1. 正则扫用户这句话
2. 映射到写死的 `prometheus_query(query="db_connections")`
3. **每次调用 spawn 一个 stdio 子进程**跑 Mock Server
4. Mock 返回固定数
5. 拼进 prompt，模型写一段话

所以 MCP 在这里是 **「带白名单的本地函数调用」**，协议本身的价值（动态工具发现、远程 server、鉴权、采样）几乎没用上。`list_tools` 有，resolver 不用。HTTP/SSE 传输预留了字段，没实现。超时 5s、无重试、结果不截断。

**这合不合理？** 作为 Phase 的占位，合理——比直接在 Agent 里写死 `requests.get(prometheus)` 多一层隔离和白名单（Prom 查询枚举、SQL 只允许 SELECT）。作为「我们已经接了 MCP」的完成态，不合理。生产里 stdio 短连接也扛不住：每次冷启动进程，延迟和文件描述符都会爆。

和 Cursor / Claude Desktop 的 MCP 比：它们是 **模型驱动 + 长连接**；你们是 **规则驱动 + 短连接 Mock**。中间至少还差：真实 Prometheus MCP、LLM tool calling、连接池、结果上限。

另外：MCP 和 RAG 的协调很弱。运维问题常常是「手册说阈值是 80%，现在 Prometheus 是多少」。图里可以并行拉，但模型没有「先查再决定还要不要查」的能力，工具参数也不能由模型填（只能四选一的枚举 query）。

## 四、对照 2025 主流，还缺什么

### RAG

你们已经补了目录清洗和标题切块，这是对的。和现在主流 RAG（Dify、LlamaIndex production、Azure AI Search）比，仍缺：

| 能力 | 你们 | 主流 |
|------|------|------|
| 检索 | 纯向量 + 阈值 | 向量 + 关键词（hybrid） |
| 重排 | 无 | cross-encoder / Cohere rerank |
| 查询改写 | 无 | HyDE / 多 query |
| 引用 | 把 chunk 塞进 prompt | 强制引用 + 幻觉校验 |
| 评测 | 无 | RAGAS / 金标集 |
| 重入库 | 删了再传 | 版本化 + 一键 rebuild |

阈值过滤和 top_k=5 在脏目录修好后会好很多，但 **「问 A 命中 B 文档标题」** 这类问题，没有 hybrid/rerank 会反复出现。Python 检索直连只读 PG 是好设计。

Embedding 无 Key 时用 hash 假向量：CI 能过，本地若忘了配 Key，检索分数是噪声。这是环境问题，但没有启动时的明显告警。

### 大文件分析

名为 Analysis Worker，实际是 **前 1MB 关键字扫描**。Heap dump / GC 日志的主流是 Eclipse MAT、async-profiler 解析、或至少按文件类型走专用 parser。现在和「上传后异步出摘要」的产品形态对上了，分析深度对不上场景三的宣传。

### 前端

Vite + 原生 JS 够演示。没有请求级 id 与 Trace 关联、没有断线重连（SSE 断了得手动再发）、没有任务完成推送（分析完要刷新文件面板）。对本地测试够用。

### 可观测性

追踪是亮点。缺口：Worker 没有 HTTP，Prometheus 抓不到它的指标；没有 Loki，排障仍靠 `docker logs`；没有告警。你这次能在 Tempo 里看到 429，说明主路径追踪是成功的。

## 五、问题优先级（本地测试阶段，淡化安全）

**会直接让演示翻车**

1. 智谱 429：无熔断/无备用模型/重试过弱  
2. 取消不中断图：关页面仍烧 embedding/LLM  
3. 规则路由误触发工具默认 `db_connections`  
4. Kafka 坏消息被 commit，job 可能悬挂  

**会让「智能」名不副实**

5. MCP 不是模型调工具，是关键词调 Mock  
6. Agent 没有工具循环，不能多步诊断  
7. RAG 无 hybrid/rerank，召回上限就是向量相似度  
8. 分析 Worker 不是真分析  

**上生产前再做（现在可挂着）**

9. Outbox、DLQ 重放、熔断、统一 timeout  
10. chunks 分批写入 / 写入账号拆分  
11. Checkpoint、HITL  
12. SSE ping、Worker 指标、集中日志

## 一句收束

工程的**骨架是 2025 企业主流**（双栈、流式网关、事件驱动入库、OTel），**肌肉还是 2023 规则流水线**（关键词路由、Mock MCP、单次 DAG、弱限流）。文档自己把这条差距写在 V1/V2 里了，代码和文档是对齐的，并没有「设计吹了、实现偷了」的诚信问题。

若下一阶段只打一个方向：把 MCP 改成 **LLM function calling + 长连接（哪怕仍打 Mock）**，同时给 LLM 429 加熔断和备用模型。这两件会立刻改变「这像不像一个 Agent」的观感，也正好吃掉你刚碰到的限流故障。想动手的话切到 Agent 模式即可。
